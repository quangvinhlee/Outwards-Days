# Nearby outdoor places

With optional approximate coordinates, the API queries a small area for mapped parks, gardens, squares, picnic sites and river features, plus hiking route relations within 60 km on the public Overpass instance or 120 km on a managed instance. OpenStreetMap data is community maintained and incomplete. No API can guarantee every outdoor place. Map entries can be stale, private in practice, or missing an entrance; the app links to their source and asks users to check access.

A short activity may name an eligible mapped outdoor place only when its straight-line distance fits a conservative lower bound on the user's one-way travel estimate. Straight-line distance is **not** a verified journey time. A river feature is a discovery link, since a mapped waterway alone does not establish bank access. If no valid named place fits, a familiar-place activity remains available.

A named hiking proposal requires the hiking interest, moderate-or-higher effort, the longer-outing setting, a mapped loop route with a distance tag, enough time for that distance at a cautious estimated pace, an OSRM driving estimate strictly below the user's one-way limit (default 180 minutes), room in the calendar for the round trip, suitable forecast/daylight, and explicit acceptance. A full free day gets priority for the one longer outing. The app does not certify route safety, difficulty, access, or exact walking duration. An unsuitable or unsourced route is never inserted into the calendar.

Completed and partly completed visits, skipped outcomes and destination IDs are used by the deterministic planner to rotate suggestions. A repeated category at the same previously visited place gets an extra penalty; suggestions that were never visited do not count as visits. The model only selects and describes choices already checked in code. Repetition is allowed when choices are limited, but nearby alternatives are preferred. The nearby browser caches its last successful result by approximate location. A saved plan also keeps its mapped place details for offline viewing.

Local development uses low-rate public Overpass queries, Photon as a nearby-park fallback, and the OSRM demo route service, with a six-hour memory and MongoDB place cache and graceful fallback to stale place results. Drive estimates go to mapped route centers, not trailheads, and omit live traffic. The demo service has no uptime guarantee; without an estimate, hiking proposals are withheld. Set `ROUTING_BASE_URL` to a managed OSRM-compatible service for production and `PHOTON_BASE_URL` to a managed Photon service if using that park source. Cache records expire after 30 days. Public Overpass servers can be overloaded and are unsuitable as the sole backend for a public app. Production place discovery needs managed Overpass via `OVERPASS_BASE_URL`; Photon only supplies parks when Overpass fails. SerpApi can add park results. OpenStreetMap data is attributed in the app and is available under ODbL. See [Photon API documentation](https://github.com/komoot/photon/blob/master/docs/api-v1.md), [Overpass API usage guidance](https://wiki.openstreetmap.org/wiki/Overpass_API#Public_Overpass_API_instances), [OSM attribution](https://wiki.openstreetmap.org/wiki/Attribution), and [hiking route tags](https://wiki.openstreetmap.org/wiki/Tag:route%3Dhiking).


## Mini missions during an outing

Each planned session includes two or three optional mini missions. Outings now include garden care, outdoor reading, movement, picnics and photography alongside walks and hikes when the user selects those interests. Gardening uses the user's own outdoor plants; mapped outings name their actual destination. Activity categories appear on the week card and detail page. Every category can ask for a short observation or feeling, not just gardening. Completed mission IDs rotate later prompts. A written note or overall feedback from a previous outing in the same category or at the same place becomes context for a later prompt; a return to the same place asks what changed. A garden observation saved after planting can become the next visit's growth-check prompt. During live Gemma generation, the model receives bounded recent categories, outcomes, completed mission IDs, photo subjects, note excerpts and feedback, then selects a reflection style from a fixed list. The app supplies the final wording and has a deterministic fallback if inference fails. These are suggestions, not claims that a particular animal or plant will be present. The app never asks for photos of children or strangers; ask a dog's owner before photographing their dog.

Action missions such as watering, weeding or listening remain manually checkable offline. Reflection missions ask for a short written observation; drafts are saved locally and the note joins the completion record when submitted. Photo missions require an accepted, started outing and a camera capture. If the original subject cannot be found, the user can choose another visible subject on the outing, such as a flower, tree, sky or texture. The API checks the photo with the configured Gemma vision model and stores only the chosen subject and verification time; it does not keep the image. A verified photo can be included in the completion event. The vision verdict is fallible and does not prove GPS location, route or capture time. The whole-outing completion control is near the top of the activity detail page and becomes available after acceptance and the scheduled start. Mini missions are optional. Existing saved plans receive stable missions when read, without regenerating the outing.

Accepting an outing after its scheduled start rechecks the original reserved time against the confirmed schedule. It does not turn the elapsed minutes into a false calendar conflict. A real overlap or changed travel/time budget still blocks acceptance. New history-aware missions can use completed outings from earlier weeks and from the current week when suggestions are regenerated; saved activity missions stay stable during an outing.
