# Implementation decisions

The app preserves the plan's separation between scheduling and language generation. The independent planner package subtracts commitments and accepted activities from user-confirmed outdoor windows. Explicit lunch gaps split only their parent work block; other commitments still block the gap. Luxon rejects missing or ambiguous local wall times. UTC instants and local dates remain attached to activities.

Outdoor windows are broad availability, not a request for the earliest possible start. By default, the planner leaves the morning before an early work shift open for waking, commuting and preparation; it reserves 30 minutes after a work shift and 60 minutes after recorded sleep. A weekday with no entered work block favors 18:00 or later unless the user marks it as a full day off or narrows the outdoor window to a specific daytime period. Weekends default to full days off in a new schedule, but the user can change each day. Ordinary full-day plans start at 09:00 or later; on a long free day an eligible longer outing may start at 08:00. Users who explicitly prefer early outings can use a morning slot after the wake buffer and before the 60-minute pre-work margin. Later shifts retain midday availability. These are conservative defaults based only on entered schedule blocks; the app does not know when someone is physically at home unless they enter their commute and commitments. Existing accepted activities are revalidated against hard calendar conflicts, so a later change of time preference does not retroactively invalidate them.

The Mastra workflow computes slots, fetches context, calls Ollama's native structured-output API, parses with Zod, and validates semantic constraints. It repairs once and then uses a labelled deterministic catalogue fallback. The scheduler chooses distinct eligible days and feasible durations first. The model selects among validated templates for each named day and personalizes wording; an internal keyed-day output schema prevents duplicate slots. The public plan remains an activity array. The server assigns final instants. It does not send raw work/sleep descriptions to the model. Model references are limited to allowed slot, template and sourced destination IDs. Code checks travel allowance, route distance, daylight, weather and recent place use before a named destination can be scheduled.

For a compact prototype, MongoDB stores each user's schedules, plans, runs and immutable completion events in one owner aggregate, plus separate hashed-token sessions and email/password account collections. Each account points to one user aggregate; authenticated routes derive that user ID from the server-side session, not a client-supplied ID. Registering an existing guest claims the same aggregate, preserving its plans and history. A compare-and-set on the aggregate revision makes acceptance, frequency checks, completion deduplication and job publication atomic without a multi-document transaction. This intentionally differs from the plan's normalized collection layout. It simplifies correctness at prototype scale but must be migrated/partitioned before long-term history approaches MongoDB's 16 MB document limit. Current plan snapshots and completion history remain embedded; previous revisions within the same week are not retained as separate documents.

Jobs are persisted before a 202 response. One worker per API process claims a job with an expiring lease and ownership token. It retries interruptions at most three times and checks schedule, preference and plan revisions before publication. Deploy exactly one API instance to preserve global inference concurrency of one; leases prevent duplicate publication across accidental overlap, but they are not a distributed global concurrency semaphore. Inference requests time out; the lease exceeds two model timeouts plus provider calls.

The SQLite completion outbox is the local source of truth for unsent events. The UI overlays pending outcomes onto server snapshots, so refresh cannot erase unsynced intent. Stable UUIDs survive retries and process restarts. Network/rate-limit/server errors remain retryable on foreground/manual refresh. Permanent failures are retained with an explanation instead of retried indefinitely. Server state computes authoritative progress by unique activity, not event count. The native queue does not currently use exponential background retry or a connectivity subscription; foreground/manual retry is intentional.

Weather and destination caches currently live in bounded API-process caches, with fetch timestamps persisted on plan activities. Weather uses daily forecast summaries and sunrise/sunset in this increment. A restart drops the provider cache but not plans or jobs. Persistent provider caching and hourly weather are follow-up improvements. Open-Meteo weather is never an AI-produced safety flag or a trail-closure service.

Reminders are reconciled on foreground and successful online refresh. A reschedule returns the activity to a suggestion, requiring explicit acceptance again. Offline completions are persisted immediately; reminder reconciliation is best-effort until a successful refresh. OS notification delivery is not guaranteed.

Community input: [Salazar's account of offline retry failures](https://dev.to/salazarismo/the-hidden-problems-of-offline-first-sync-idempotency-retry-storms-and-dead-letters-1no8) and its discussion informed retained permanent failures and stable retry IDs. This is one implementation account, not consensus. We did not adopt its incidental claim about JavaScript property ordering or its application-specific six-state architecture verbatim.
